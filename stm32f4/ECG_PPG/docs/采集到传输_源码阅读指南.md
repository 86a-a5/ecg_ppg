# ECG_PPG 下位机：从采集到数据传输的源码阅读指南

更新：下文是修复前的阅读与问题定位记录。2026-10-16 已完成修复、烧录和 COM13
实机联调；最新执行方式、时钟设置、50 Hz 陷波和验证结果见
[采集联调说明](../../../host_pc/采集联调说明.md)。
本记录中的旧行号、16 MHz HSI 配置和“当前缺陷”不再代表修复后的运行状态。

阅读对象：STM32F411CEU6 工程 ECG_PPG，依据 2026-10-16 当前目录中的源码。本文解释实际编译路径，并把设计意图与实现问题分开；没有修改固件源码，也没有连接硬件验证。

这个工程的主要职责是：采集 AD8232 心电模拟输出和 MAX30102 的 RED/IR 数字数据，附加时间戳，封装成二进制帧，经 USART2 上传。当前有效执行路径没有下位机血压推理、数字滤波或心率/血氧计算。

**先沿数据方向看全貌。**

~~~mermaid
flowchart TD
    A["AD8232 模拟输出"] --> B["PA0 / ADC1：12 位"]
    T["TIM2：每 5 ms 发出 TRGO"] --> B
    B --> C["DMA2 Stream0：循环写 2 个 uint16"]
    C --> D["ADC 半满 / 全满回调"]
    D --> E["STREAM_PushECG：读取 TIM5 并组帧"]
    P["MAX30102 内部转换：100 对 RED/IR 每秒"] --> F["传感器内部 FIFO"]
    F --> G["PB6/PB7 软件 I²C：主循环轮询"]
    G --> H["最多读取 8 对，估算各点时间戳"]
    H --> I["STREAM_PushPPGAt：18 位右移 2 位并组帧"]
    E --> Q["共用字节环形发送队列"]
    I --> Q
    Q --> U["STREAM_ProcessTx"]
    U --> V["DMA1 Stream6 → USART2 TX / PA2"]
    V --> W["外接 USB-TTL → PC 串口解析器"]
    K["TIM5：1 MHz、32 位时间基准"] -.-> E
    K -.-> H
~~~

图中的串口持续发送是设计链路；当前源码中的完成中断与队列算法有缺陷，见后面的具体说明。

**理解这几个词，就能顺着代码读。**

| 名称 | 在本工程里的作用 |
|---|---|
| ADC | 把 PA0 上的模拟电压转换为 0～4095 的数字 |
| TRGO | 定时器输出的内部触发信号；TIM2 用它通知 ADC 开始一次转换 |
| DMA | 按外设请求自动搬运数据；这里分别用于 ADC→RAM 和 RAM→UART |
| 中断 / 回调 | 事件发生后 CPU 进入中断处理，再由 HAL 调用本工程定义的回调 |
| FIFO | MAX30102 内部保存尚未读取样本的先入先出存储区 |
| 环形发送队列 | STM32 RAM 中保存已经打包、等待发送的字节，和传感器 FIFO 是两个不同缓冲 |
| HAL | ST 的外设驱动层；业务代码通过 HAL 配置、启动外设和处理事件 |

**上电初始化决定后续链路如何运行。**

入口在 [main.c](../Core/Src/main.c)。执行顺序为：

~~~text
HAL_Init
  → SystemClock_Config
  → GPIO / DMA / ADC1 / TIM2 / TIM5 / USART2 初始化
  → MAX30102_Init
  → 启动 TIM5
  → STREAM_Start 清空发送队列、序号和统计量
  → 启动 TIM2
  → AD8232_Start 启动 ADC + DMA
  → 进入 while (1)
~~~

SystemClock_Config 使用标称 16 MHz 的 HSI，不使用 PLL，AHB/APB1/APB2 均不分频。后面的 200 Hz、1 MHz 计算来自这个配置，不能按芯片最高主频计算。

主循环的有效逻辑只有三步：

~~~c
MAX30102_DrainFifo();   // 主动读取 PPG，并把 PPG 帧入队
STREAM_ProcessTx();    // 尝试启动一段串口发送
HAL_Delay(2);          // 至少等待相应 HAL 毫秒节拍
~~~

ECG 不需要在主循环里调用“读取函数”，因为它由硬件触发、DMA 搬运和中断回调推进。HAL_Delay 不会关闭中断，所以等待期间 ECG 仍可被采集和入队。一次主循环还包含软件 I²C 操作等耗时，因此循环周期不是严格的 2 ms。

MAX30102 初始化失败，或 ADC DMA 启动失败，主程序会进入 Error_Handler：关闭中断并停在死循环。当前没有失败重试主循环或串口错误报告。

**ECG：一次心电采样是怎样进入发送队列的。**

AD8232 给 STM32 的是模拟输出，接在 PA0。GPIO 模拟模式和 ADC 通道 0 在 [adc.c](../Core/Src/adc.c) 配置。

TIM2 设置见 [tim.c](../Core/Src/tim.c)：

~~~text
TIM2 输入时钟 = 16,000,000 Hz
PSC = 15       → 计数频率 = 16,000,000 / (15 + 1) = 1,000,000 Hz
ARR = 4999     → 更新频率 = 1,000,000 / (4999 + 1) = 200 Hz
每 5 ms 产生一次更新事件，并输出 TRGO
~~~

ADC1 配置见 [adc.c](../Core/Src/adc.c)：12 位、单通道、右对齐、关闭连续转换、在 TIM2 TRGO 上升沿转换一次。这里的“关闭连续转换”不表示只能采一次；每次新的 TRGO 都会启动下一次转换。

ADC 的采样时间配置为 84 个 ADC 时钟周期，ADC 时钟来自 PCLK2/4；这决定一次转换中的采样阶段长度。**200 Hz 的样本间隔由 TIM2 决定**，不是由“84 cycles”决定。

AD8232_Start 调用 HAL_ADC_Start_DMA，目标为两个 uint16：

~~~c
static uint16_t ecg_dma_buffer[2];
HAL_ADC_Start_DMA(&hadc1, (uint32_t *)ecg_dma_buffer, 2U);
~~~

DMA 配置是 DMA2_Stream0 / Channel 0，外设到内存，16 位宽，内存地址递增，循环模式。HAL API 的指针强转不改变实际搬运宽度；宽度由 DMA 的 HALFWORD 配置决定。

缓冲区循环过程：

~~~text
第 1 点 → buffer[0] → 半满回调
第 2 点 → buffer[1] → 全满回调
第 3 点 → buffer[0] → 半满回调
第 4 点 → buffer[1] → 全满回调
……
~~~

所以半满回调每秒约 100 次，全满回调每秒约 100 次，合起来处理每秒 200 个心电点。“全满”在这里仅表示两个元素都写过一轮，不是一次得到一大块波形。

沿调用关系继续看：

~~~text
DMA2_Stream0_IRQHandler
  → HAL_DMA_IRQHandler(&hdma_adc1)
  → HAL 内部 ADC DMA 回调
  → HAL_ADC_ConvHalfCpltCallback / HAL_ADC_ConvCpltCallback
  → 取 buffer[0] / buffer[1]
  → STREAM_PushECG
  → STREAM_PushECGAt
  → STREAM_PushFrame
~~~

业务回调在 [AD8232.c](../BSP/Src/AD8232.c)，IRQ 入口在 [stm32f4xx_it.c](../Core/Src/stm32f4xx_it.c)。HAL_ADC_Start_DMA 已把 DMA 的完成回调与 ADC 处理函数关联起来，所以用户回调不需要由 main 手动调用。

这条路径上传 ADC 原始码值。AD8232_ToMilliVolt 虽已定义，但当前上传路径没有调用它。它按 (raw - 2048) × 3300/4096 估算相对中点电压，单位 mV；这是 AD8232 输出端相对偏置的电压，还不能直接当作电极输入端电压，后者还涉及模拟前端增益。

AD8232_IsLeadsOff 当前恒返回 0，没有真实导联脱落检测。头文件中“0.5 Hz 高通 + 40 Hz 低通”的说法也不能仅凭软件确认：AD8232 的滤波截止频率依赖外围电路。器件手册说明其高通、低通滤波可调，实际模块要结合原理图核对。[AD8232 官方数据手册](https://www.analog.com/media/en/technical-documentation/data-sheets/ad8232.pdf)

**PPG：传感器先采样，STM32 再把数字样本取回来。**

MAX30102 的 ADC 在传感器内部。STM32 读取它的数字结果，不使用 STM32 ADC1 采 PPG。硬件接口定义见 [MAX.h](../BSP/Inc/MAX.h)：PB6=SCL，PB7=SDA。

这两个引脚被配置为开漏输出；软件通过 HAL_GPIO_WritePin 拉低或释放线路，并用 HAL_GPIO_ReadPin 读取 SDA。对应代码在 [MAX.c](../BSP/Src/MAX.c)。工程没有使用 HAL_I2C_Mem_Read 这一类硬件 I²C API。

驱动按位发送 I²C 地址、寄存器地址和数据，处理 ACK，并完成 START / 重复 START / STOP。每个基础延时为 4 μs，借助 DWT 周期计数器实现；DWT 在 MAX30102_Init 中使能。这个 DWT 用于通信延时，TIM5 才用于上传时间戳。

MAX30102_Init 的主要步骤在 [MAX.c](../BSP/Src/MAX.c)：恢复总线、读取并检查 PART_ID=0x15、复位、清 FIFO 指针、写入配置、回读模式。关键寄存器如下：

| 寄存器 | 写入值 | 当前含义 |
|---|---|---|
| FIFO_CONFIG / 0x08 | 0x0F | 不做多点平均；关闭 FIFO rollover；配置 almost-full 阈值 |
| MODE_CONFIG / 0x09 | 0x03 | 同时获取 Red 与 IR 的 SpO2 模式 |
| SPO2_CONFIG / 0x0A | 0x27 | 4096 nA 量程、100 样本对/秒、411 μs 脉宽、18 位转换 |
| LED1_PA / 0x0C | 0x24 | 配置 Red LED 驱动电流 |
| LED2_PA / 0x0D | 0x24 | 配置 IR LED 驱动电流 |

0x27 的采样率和分辨率按官方手册的寄存器表核对。“SpO2 模式”说明通道和采样配置，本身不表示固件已经计算出血氧。[MAX30102 官方数据手册](https://www.analog.com/media/en/technical-documentation/data-sheets/max30102.pdf)

主循环调用 MAX30102_DrainFifo，再调用 MAX30102_ReadRawFIFO。后者读取中断状态、写指针、溢出计数和读指针，通常按下面的式子判断积压数量：

~~~c
available = (write_pointer - read_pointer) & 31;
count = min(available, max_samples);   // 主循环传入 max_samples=8
~~~

MAX30102 FIFO 深度为 32，指针按 32 回绕，所以这里按位与 31 的算法符合其环形长度。满/空指针相同的情况，驱动还结合溢出计数与数据就绪标志尝试判断。

每个样本对读取 6 字节：前三个字节组合 RED，后三个字节组合 IR，并用 0x03FFFF 保留有效 18 位：

~~~text
RED = ((b0 << 16) | (b1 << 8) | b2) & 0x03FFFF
IR  = ((b3 << 16) | (b4 << 8) | b5) & 0x03FFFF
~~~

注意两处注释容易误导：MAX30102_DrainFifo 每轮最多取 8 对，不保证一次清空整个 FIFO；MAX30102_ReadRawFIFO 内部逐点调用 MAX30102_ReadFIFO，所以每一对仍各自发起一次读事务，没有把 N×6 字节合为单次 I²C burst。

100 Hz 的采样由 MAX30102 自己的配置决定。主循环约每几毫秒查询一次，只决定“多久取一次货”，不会把传感器采样率改成 500 Hz。32 对 FIFO 在 100 Hz 下对应约 320 ms 的名义存储跨度，不能无限容忍主循环停顿。

MAX30102_Update 是另一条单点接口，当前 main 不调用。MAX.c 末尾旧的心率、血氧计算代码位于 #if 0 中，不参与编译；当前主链路也不执行手指检测和数字滤波。

**时间戳：两路有共同计时器，但采样时刻的精度不同。**

TIM5 配置在 [tim.c](../Core/Src/tim.c)：PSC=15，ARR=0xFFFFFFFF。按当前标称时钟，它每 1 μs 加 1，约 71.58 分钟回绕。

STREAM_TimestampUs 直接读取 TIM5 的计数值。ECG 在 ADC DMA 回调中读取它，因此标的是“转换完成并进入软件处理附近的时间”，包含转换耗时和中断响应延迟，没有硬件锁存触发瞬间。

PPG 的时间处理在 [main.c](../Core/Src/main.c)。程序先读取一批数据，再把该批最后一对当作当前时刻，其余按 10 ms 倒推：

~~~text
timestamp[i] = newest_us - (sample_count - 1 - i) × 10000

例：读取 3 对后 TIM5=1,000,000 μs
第 1 对 →   980,000 μs
第 2 对 →   990,000 μs
第 3 对 → 1,000,000 μs
~~~

这种处理避免同一批所有样本共用一个时间戳，但仍是估计。它包含样本等待轮询、软件 I²C 读取耗时，也假设传感器严格保持标称 100 Hz。若 FIFO 里超过 8 对，当前取出的“最后一对”仍不是整个 FIFO 最新的点，直接锚定为当前时刻会造成更大误差，后续批次还可能重叠。

初始化次序也要留意：MAX30102 在 TIM5 启动前已经开始转换，启动 TIM5 后没有同步清空传感器 FIFO。若最初倒推跨度超过 TIM5 已运行时间，uint32 相减会下溢到接近回绕点。

因此，源码注释里的“天然时间对齐”只能理解为两路使用同一时间数值基准，不能据此认定两路已实现精确同步采样。后续用 ECG 与 PPG 的峰值时差做分析时，需要单独评估这个误差。

**组帧：每个采样点究竟发出哪些字节。**

协议常量在 [ecg_ppg_stream.h](../BSP/Inc/ecg_ppg_stream.h)。每帧固定 12 字节，多字节整数按小端序排列：

| 字节位置（从 0 开始） | ECG 帧 | PPG 帧 |
|---|---|---|
| 0 | 0xAA 帧头 | 0xAA 帧头 |
| 1 | 0x01 类型 | 0x02 类型 |
| 2 | 共用的 8 位递增序号 | 共用的 8 位递增序号 |
| 3～4 | uint16 ADC 原始值 | uint16 (RED >> 2) |
| 5～6 | 0xFF、0xFF 填充 | uint16 (IR >> 2) |
| 7～10 | uint32 微秒时间戳 | uint32 微秒时间戳 |
| 11 | 0x55 帧尾 | 0x55 帧尾 |

具体组帧见 [ecg_ppg_stream.c](../BSP/Src/ecg_ppg_stream.c)。例如 ECG=2048，序号=42，时间戳=1,000,000 μs：

~~~text
AA 01 2A 00 08 FF FF 40 42 0F 00 55
         └───┘       └─────────┘
        0x0800         0x000F4240
~~~

PPG 把 18 位结果右移 2 位是为了装入 uint16。这会丢失最低 2 位；PC 左移 2 位只能恢复量级，不能恢复已丢失的信息。例如 131073 上传后再展开为 131072。

ECG 与 PPG 共用一个序号，按组帧尝试递增并在 255 后回到 0。序号不保证“两个 ECG、一个 PPG”严格交替，也不代表两路样本的配对关系。FIFO 中在组帧前就丢失的样本不会消耗序号，因而序号连续也不能证明采集端零丢样。

协议没有 CRC 或校验和。帧头、类型、帧尾等结构检查可以辅助重新找帧，但不能可靠检测所有载荷误码。

**队列和发送：为什么采集回调不直接调用阻塞 UART。**

串口线上发送一帧需要时间。采集回调只组帧并把 12 字节复制入队，然后尽快返回；主循环负责发起发送，以减少通信等待对采集处理的影响。

发送层的状态在 [ecg_ppg_stream.c](../BSP/Src/ecg_ppg_stream.c)：

| 状态 | 作用 |
|---|---|
| tx_buffer | 待发送的字节存储区 |
| tx_head | 下次写入位置 |
| tx_tail | 最早尚未释放的待发送位置 |
| tx_busy | 已启动的 DMA 发送尚未完成 |
| tx_dma_ready | 初始化时检查 UART DMA 句柄是否存在 |

STREAM_PushFrame 在短暂关闭中断的临界区内检查空间并复制整帧，防止 ECG 中断与主循环同时修改队列。空间不足时丢弃新帧并增加 tx_dropped，不等待发送完成。

STREAM_ProcessTx 在没有忙碌传输时，计算从 tx_tail 到数组末尾可连续发送的字节数，调用 HAL_UART_Transmit_DMA。一个 DMA chunk 可能包含多帧，也可能在数组边界切开一帧；UART 是字节流，PC 应使用接收缓冲拼帧，不能把一次 read 当作一帧。

UART 配置见 [usart.c](../Core/Src/usart.c)：USART2，PA2=TX，PA3=RX，115200、8 数据位、无校验、1 停止位，无硬件流控。发送 DMA 为 DMA1_Stream6 / Channel 4，内存到外设、字节宽度、普通模式。

主程序使用的是 USART2 字节接口。USB-TTL 是外部桥接设备，不是本固件实现的 USB CDC；当前有效源码也没有蓝牙 AT 初始化或蓝牙连接管理。虽然 USART 配为 TX_RX，当前程序没有启动接收，也没有上位机命令解析。

按设计数据量计算：

~~~text
ECG：200 帧/秒 × 12 字节 = 2400 字节/秒
PPG：100 帧/秒 × 12 字节 = 1200 字节/秒
合计：3600 字节/秒
115200、8N1：每字节在线上占 10 位 → 理论 11520 字节/秒
占用：约 31.25%
~~~

这些数字说明标称 UART 带宽足够；它们不能证明完成中断、缓冲算法或外部传输端已可靠工作。无流控 UART 也不会感知 PC 应用是否暂停读取，因此不能把“电脑暂停”直接等同于 STM32 队列自动背压。

如果 DMA 句柄不存在，或 DMA 启动返回失败，代码退回 HAL_UART_Transmit，每次最多 48 字节，超时参数 20 ms。这个回退会阻塞主循环，且目前忽略发送返回值、仍推进 tx_tail，失败时可能静默丢数据。

**当前代码中需要明确认识的实现缺陷。**

1. **普通 DMA 发送的完成链没有接完整，会阻止持续上传。**

   本工程使用的 HAL 在 UART DMA 普通模式下，DMA 完成只表示数据已搬到串口外设。HAL 的 UART_DMATransmitCplt 会使能 UART TC 中断，等待最后一字节真正发完；随后 USART2_IRQHandler 必须调用 HAL_UART_IRQHandler，才会到达 HAL_UART_TxCpltCallback。

   正确的事件关系应当是：

   ~~~text
   DMA1_Stream6_IRQHandler
     → HAL_DMA_IRQHandler
     → UART_DMATransmitCplt
     → 开启 UART TC 中断
     → USART2_IRQHandler
     → HAL_UART_IRQHandler
     → UART_EndTransmit_IT
     → HAL_UART_TxCpltCallback
     → STREAM_TxCompleteFromISR
     → 推进 tx_tail，清除 tx_busy
   ~~~

   当前 usart.c 仅使能 DMA1_Stream6_IRQn，没有使能 USART2_IRQn；stm32f4xx_it.c 也没有 USART2_IRQHandler。因而按当前源码推断，首次成功 DMA 发送后 tx_busy 无法通过正常完成回调清零，后续 STREAM_ProcessTx 将持续提前返回。这里是源码推断，尚未以板上现象验证。

   依据：[HAL UART 普通 DMA 完成实现](../Drivers/STM32F4xx_HAL_Driver/Src/stm32f4xx_hal_uart.c)、[HAL UART 最终发送完成处理](../Drivers/STM32F4xx_HAL_Driver/Src/stm32f4xx_hal_uart.c)、[当前中断入口](../Core/Src/stm32f4xx_it.c)。

2. **发送队列长度是 3072，回绕算法却要求长度为 2 的幂。**

   STREAM_TX_QUEUE_FRAMES=256、STREAM_FRAME_LENGTH=12，得到 N=3072。代码使用 (index+1)&(N-1) 回绕，并用同类按位与计算占用量；这只有 N 为 2 的幂时才能替代取模。

   直接演算：1024 & 3071 = 0，因此写指针到 1023 后就提前返回 0，而不是继续写 1024。离线枚举也确认，从 0 开始只遍历 1024 个不同下标。它既不是正确的 3072 字节队列，占用量计算也不一致，可能覆盖尚未发送的数据。

   所以头文件宣称“约 0.9 秒缓存”只是意图。即使修正为正确取模，当前保留一个空字节的设计也只能完整容纳 floor(3071/12)=255 帧，名义约 0.85 秒。

   依据：[队列长度与占用计算](../BSP/Src/ecg_ppg_stream.c)、[写指针回绕](../BSP/Src/ecg_ppg_stream.c)。

3. **两路共用 frame_scratch，组帧过程并没有被完整保护。**

   PPG 在主循环中写这个全局数组，ECG 在 ADC 中断中也写它。STREAM_NextSequence 只保护序号递增，STREAM_PushFrame 只保护最终入队；二者之间写帧内容的过程可以被中断打断。

   例如 PPG 已写类型和部分载荷时，ECG 中断进入并把整个 frame_scratch 改为 ECG 帧；返回主循环后，PPG 继续写剩余字节，最终可能入队混合内容。可采用每次调用独立的局部帧数组解决共享暂存问题，但本次没有修改实现。

   依据：[共享暂存数组](../BSP/Src/ecg_ppg_stream.c)、[两路组帧函数](../BSP/Src/ecg_ppg_stream.c)。

4. **统计字段不能直接按注释当作测量结果。**

   tx_frames 统计成功入队，不表示 UART 实际发送完成，也不表示 PC 收到。ecg_queue_errors 实际在 ECG 帧入队失败时递增，并没有检测 ADC DMA 缓冲被覆盖。STREAM_CountPpgFifoOverflow 只有定义，没有在当前 FIFO 读取路径中调用，所以 ppg_fifo_overflows 可能一直是 0。

   main.c 的调试注释提及 LED 和 ASCII 行，但当前执行路径没有相应定期输出实现。诊断时应结合代码调用位置理解统计量。

5. **CubeMX 配置文件与当前 C 代码没有保持一致。**

   [ECG_PPG.ioc](../ECG_PPG.ioc) 中 TIM2.Period=1999，按相同分频会得到 500 Hz；当前 tim.c 的 Period=4999 才是 200 Hz。ioc 也没有当前 USART2 和 TX DMA 配置。TIM5 的 32 位最大 Period 也只在当前 C 文件中明确设置。

   解释当前固件时应以实际参与编译的源码为准；以后用 CubeMX 再生成代码，需要核对是否覆盖这些手工配置。

**PC 怎样把字节重新变成两条波形。**

配套上位机的接收循环在 [serial_ecg_ppg_gui.py](../../../host_pc/src/ecg_ppg/gui/serial_ecg_ppg_gui.py)：打开串口、读取任意长度字节块，再交给 FrameParser.feed。

解析器在 [ecg_ppg_protocol.py](../../../host_pc/src/ecg_ppg/acquisition/ecg_ppg_protocol.py) 累积接收缓冲，寻找 0xAA，等待至少 12 字节，检查帧结构，按类型分流，再解析小端数据和时间戳。PPG 左移 2 位恢复近似的 18 位量级，时间戳另做 32 位回绕展开。

后续记录到 CSV 的入口在 [ecg_ppg_record.py](../../../host_pc/src/ecg_ppg/acquisition/ecg_ppg_record.py)。ECG 200 Hz 与 PPG 100 Hz 的数组长度本来就不同，数据对齐应看时间戳，而不是直接把两数组相同下标当成同一采样时刻。

本次运行了现有协议解析器自检：构造帧得到 ECG 10 帧、PPG 10 帧、1 次时间戳回绕、0 个坏帧、0 个序号丢帧。这个结果仅验证构造协议数据的解析路径，不验证板上采集、时间估计或 UART DMA 连续上传。
